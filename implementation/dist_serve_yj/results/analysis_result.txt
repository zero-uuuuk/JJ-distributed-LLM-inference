
==================================================
실험 개요
==================================================

[대상 모델] facebook/opt-6.7b (8-bit 양자화)
[실험 환경] AWS EC2 g4dn.xlarge  /  NVIDIA T4 GPU (16 GB VRAM)
[측정 지표] Prefill Latency, Throughput (B×L / latency), GPU Utilization
[반복 횟수] Phase1: 8회 / Phase2: 20회 (per config)
[입력 구성] 고정 랜덤 시드(42) input_ids, use_cache=False (prefill-only)

==================================================
종합 해석 — DistServe 논문과의 대조
==================================================

[1] Batch가 클수록 Lm이 낮아진다  ✓ 실측 확인
    - B=1: Lm ≈ 1,536   B=8: Lm ≈ 512
    - 배치가 클수록 짧은 프롬프트만으로도 GPU가 포화됨

[2] Lm 이후 throughput 포화, latency 만 증가  ✓ 실측 확인
    - B=8, L=512→1024: throughput +0.05%, latency +100%
    - DistServe "compute-bound 초과 시 latency만 늘고 효율 없음" 가설 부합

[3] compute-bound 전환 임계 (총 토큰 수 기준)
    - B×L ≈ 1,500 ~ 4,000 구간에서 GPU util 80~92% 도달
    - T4 GPU 기준 약 3,000~4,000 total tokens가 prefill 포화 임계

[4] VRAM 여유 충분  ✓
    - 최대 B=8, L=2048에서 7,181 MB 사용 (T4 16GB 대비 45%)
    - OOM은 compute 포화 이전에 발생하지 않음
    - DistServe의 "prefill은 compute-bound, 메모리 한계가 아님" 주장 부합

[5] DistServe 스케줄링 시사점
    - Lm 이하 요청은 배치로 묶어 처리 → throughput 이득
    - Lm 이상 요청은 개별 스케줄링 → latency 제어
    - 본 실험 결과를 기반으로 T4 환경의 Lm 표를 위와 같이 결정

==================================================
실험 한계 (Limitations)
==================================================

[1] 단일 GPU / 단일 노드 환경
    - 실제 DistServe는 Prefill·Decode 인스턴스를 물리적으로 분리
    - 본 실험은 분리 없이 단일 T4 GPU에서 prefill-only 측정
    - 파이프라인·PD 간섭(interference) 효과는 측정되지 않음
    - → Lm 값이 실제 분산 환경과 다를 수 있음

[2] 모델 크기 및 GPU 등급의 제약
    - OPT-6.7B 8-bit은 실제 프로덕션 모델(70B+)보다 훨씬 작음
    - T4는 논문에서 상정한 A100/H100 대비 컴퓨팅 성능 약 10배 차이
    - Lm 절댓값(토큰 수)은 GPU 등급·모델 크기에 비례하여 달라짐
    - → 본 결과를 다른 모델·GPU에 그대로 일반화 불가

[3] Batch size 범위 제한 (최대 8)
    - DistServe 논문은 더 넓은 배치 범위(16, 32, 64)를 다룸
    - T4 VRAM 한계(16GB)로 B=16 이상은 OOM 위험으로 미측정
    - B=8 이상에서 Lm이 더 낮아지는 경향을 확인하지 못함

[4] 고정 랜덤 입력만 사용
    - 실제 워크로드는 언어적으로 다양한 attention 패턴을 가짐
    - 고정 랜덤 seed input은 attention sparsity·locality 재현 불가
    - 실제 텍스트 대비 latency에 ±5~15% 오차 가능성

[5] nvidia-smi 수집 간격의 한계 (1초)
    - nvidia-smi 폴링 주기 1초 → latency < 1초 구간에서 GPU util
      측정이 부정확 (B=1 L=128: latency 112ms → 1회 샘플에 의존)
    - 짧은 latency 구간의 GPU util 값은 참고 수준으로만 사용

[6] Decode 단계 미측정
    - prefill-only (use_cache=False) 실험으로 decode TTFT·TPOT 미포함
    - Lm은 prefill compute saturation 기준이며,
      decode memory-bound 특성은 별도 실험 필요

[7] Spot Instance 환경 가변성
    - AWS Spot 인스턴스 특성상 host noisy-neighbor 효과 존재 가능
    - 단일 실행 시점의 결과이므로 시간대·노드 따라 ±5% 편차 가능성
    - 복수 실행 앙상블 또는 On-Demand 인스턴스로 재검증 권장
